title: Release channels
description: How a HyperFrames release is cut and what it ships.
---

HyperFrames publishes two release channels:

- Stable releases use versions like `0.9.0` and become the GitHub release that `install.sh` installs by default.
- Prereleases use versions like `0.9.1-rc.1` and are marked as GitHub prereleases, so only an explicit `HYPERFRAMES_VERSION` installs them.

## Cutting a release

Publishing a GitHub release is the trigger. The Release workflow then builds, smoke-tests and attaches the standalone binaries (darwin-arm64, linux-x64, linux-arm64, each with a `.sha256`) and the portable agent plugin.

1. Bump every package and plugin manifest to the new version, then merge it to `main`:

   ```bash
   bun run set-version 0.9.0 --no-tag
   ```

   To write reviewed release notes, first run `bun run changelog:draft 0.9.0 --write`. It drafts `releases/v0.9.0.md` and the `docs/changelog.mdx` entry; replace their TODO summaries before merging. See [Changelog process](/contributing/changelog-process).

2. Publish the release on that commit, from the GitHub UI or with:

   ```bash
   gh release create v0.9.0 --target main --generate-notes
   # or: --notes-file releases/v0.9.0.md
   ```

   For a prerelease, tick "Set as a pre-release", or pass `--prerelease`.

The workflow fails before building anything if the tag's version differs from `packages/cli/package.json`. A binary reports its package version, and `render --docker` downloads the release named after it, so the two must agree. To fix a mismatch, delete the release and its tag, merge the version bump, and publish again.

To rebuild the assets of an existing release, run the Release workflow manually with its tag. Uploads use `--clobber`, so a re-run replaces them.

## Installing a prerelease

```bash
HYPERFRAMES_VERSION=0.9.1-rc.1 sh -c "$(curl -fsSL https://raw.githubusercontent.com/ryu1845/hyperframes/main/install.sh)"
```
